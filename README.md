# Spun: laundry pickup & delivery prototype

A working prototype you can run on your own computer. It covers the Spun customer app, driver app, and laundromat partner / admin console for the **Humber Bay Shores / Mimico pilot (postal FSA M8V)**. Customers pay **per bag**. Partner laundromats do the washing, and Spun drivers pick up and deliver in 2-hour windows with next-day turnaround.

> "Spun" is a working name. To rename the app, see [Renaming / rebranding](#renaming--rebranding).
> Nothing here is deployed or published, and no external accounts were created. Payments are **mock / Stripe test mode only**.

---

## Run it

Requires **Node.js 20.19+** (tested on Node 20.19.2). No database server or native build tools are needed (SQLite runs as WebAssembly via `sql.js`).

```bash
cd spun-app
npm install
npm start            # builds the web app and serves everything on http://localhost:3000
```

Open **http://localhost:3000** and pick a demo login. The first start seeds demo data into `data/spun.db` automatically. Stop the server with `Ctrl+C`.

| Command | What it does |
|---|---|
| `npm start` | Build the client, then serve API + app on port 3000 (`PORT=…` to change) |
| `npm run dev` | Hot-reload development: API on :3000 + Vite on **http://localhost:5173** |
| `npm run seed` | Wipe and re-seed demo data (or use **Admin → Overview → Reset demo data**) |
| `npm run e2e` | Build, start a throwaway server on :3100 (separate DB), click through every flow in headless Chrome, and write `screenshots/` + `screenshots/e2e-results.txt` |

`npm run e2e` uses an installed Chrome/Chromium (`/usr/bin/google-chrome` by default; set `CHROME_PATH=…` to override). It does not download browsers.

## What it does

1. **Signup with zone check.** The postal code is validated as Canadian and checked against allowed prefixes, with a live hint as you type. In-zone signups create an account and require photo consent, per the service-standards photo/privacy notice. Out-of-zone signups are saved to a **waitlist** and shown a "not in your area yet" message. The zone list is configurable (see below).
2. **Booking.** Choose Small / Standard / Large (+ extra Standard bags), then a date (next 14 days, Sunday closed) and a 2-hour window. Add-ons are hang-dry per item, same-day, and comforters/blankets. The order summary shows your preferences. The live price summary in CAD shows subtotal, the **first-order promo**, a **13% HST** line and the total. Expected delivery is calculated: next service day evening, Saturday → Monday, same-day → by 9 pm.
3. **Subscriptions.** Weekly / Biweekly × Standard / Small, with pickup day + window. Plans are billed every 4 weeks (mock). The plan auto-schedules its next pickup and schedules the following one when each plan order is delivered. You can **change day/window, pause, resume and cancel**. Pausing or cancelling cancels the open plan pickup.
4. **Preference profile.** Detergent, softener, bleach, wash temp, dryer heat, hang-dry items (+ "all activewear"), folding style, sort, kids separate, allergies, building access, and notes (max 200 characters). Preferences are **snapshotted onto every order**, and orders still *scheduled* are refreshed when you edit. Coloured-dot flags follow service-standards §2: 🟢 unscented/hypo, 🔵 hang-dry, 🔴 allergy/own detergent.
5. **Tracking.** Five-step progress bar (Scheduled → Picked up → At laundromat → Ready → Delivered), a timestamped timeline with who did what, and **photo slots** for Pickup (Photo 1), Laundromat intake (Photo 2) and Delivery (Photo 4). Slots show real uploads or placeholders. Each order shows bag tag IDs in the `YYMMDD-NN-B#` format.
6. **Driver.** Route for a date (prev/next day): pickups and deliveries ordered by window, then address. Each stop shows the address, window, bag count/tags, extras, flags, building access, notes and full preferences. **Take photo** uses `<input type="file" accept="image/*" capture="environment">`, so a phone opens its camera. Photos are stored in `uploads/`. **Mark picked up / delivered stays disabled until the photo is taken** (server-enforced too). "Dropped at laundromat" moves a picked-up order on.
7. **Admin / partner.** Order table (card layout on mobile) with status filter chips + counts and search. Each row shows preferences, a one-click **advance** (At laundromat, Ready; admin can also do picked up / delivered / cancel), and admin **driver assignment**. The order detail page has full preferences, timeline and intake photo upload. The partner role sees only its own orders, with the customer ID instead of name, address or phone (service-standards §2/§7 privacy). Admin overview shows status counts, the zone config, the waitlist, subscriptions, mock revenue and a reset button.

## Architecture (plain language)

- **One small Node server** (`server/index.js`, Express) does everything: it serves the web app, answers `/api/...` requests, and saves photo uploads to `uploads/`.
- **The database is a single file**, `data/spun.db` (SQLite through `sql.js`, a WebAssembly build, so `npm install` needs no compiler). Tables: users, preferences, orders, order_events (the timeline), photos, subscriptions, payments, waitlist, partners. Delete the file or run `npm run seed` to start fresh.
- **The web app** (`web/`, React + Vite) is one mobile-first app. What you see depends on the role you picked: customer screens, driver route, or the partner/admin console.
- **Business rules live in one place**, `shared/`, which both the server and the browser use:
  - `shared/config.js`: brand, zone, windows, bag tiers, add-ons, plans, HST, statuses, preference options
  - `shared/logic.js`: price calculation, postal/zone checks, slot availability, delivery date

  The browser shows live prices, but **the server recalculates everything** at checkout.
- **Status changes are role-checked on the server.** A driver can't mark something Ready, a partner can't mark it Delivered, and a customer can only cancel a scheduled pickup. Every change writes a timeline event.
- `server/payments.js` holds the mock checkout and the Stripe test-mode hook. `server/seed.js` holds the demo data. `scripts/e2e.js` is the automated click-through + screenshots.

## What's mocked / not real

| Area | Prototype behaviour |
|---|---|
| **Login** | Demo role switcher. The browser sends the chosen user id in a header (`x-user-id`). **Not secure.** Replace with real auth before any real use |
| **Payments** | **Mock checkout** that imitates Stripe test cards (`4242 4242 4242 4242` succeeds, `4000 0000 0000 0002` is declined). No network calls, no keys. Plans are "charged" once at signup. No recurring billing job runs |
| **Stripe test mode** | Optional code path, **untested** (no Stripe account was created). See below |
| **SMS / email** | None. Texts ("picked up", overstuffed bag, delivered + photo) and waitlist emails are not sent |
| **Photos** | Saved to the local `uploads/` folder. Seeded photos are drawn SVG placeholders. No 90-day retention job |
| **Routing** | Stops sorted by window, then address. No maps, ETAs or optimisation. Driver assignment is "least busy that day" by default, and admin can reassign |
| **Clock** | Actions use the real clock. On a Sunday (closed) the driver acts on Monday's route, so their timestamps are "today" |
| **Partner** | One partner (Paul's Laundromat, from the prospects list) handles all orders. Partner weigh log / invoicing is not built |
| Not built | Overstuffed-bag upsize / wet-bag fee flow, claims, ratings, missed pickup/delivery fees, item counts, order-sheet printing, referral credits, promo codes |

### Dropping in Stripe test keys later

1. `cp .env.example .env`
2. Fill in `STRIPE_SECRET_KEY=sk_test_...` (and optionally `STRIPE_PUBLISHABLE_KEY=pk_test_...`) from the Stripe dashboard in **Test mode**.
3. Restart. The footer then says "Stripe TEST mode". Checkout creates a hosted **Stripe Checkout Session** (`server/payments.js` → `createStripeCheckout`) for the HST-inclusive total and redirects to Stripe. On return, `/api/checkout/:ref/stripe-return` verifies the session is paid, then creates the order or plan.
4. Keys that don't start with `sk_test_` are **refused**, and the app falls back to mock.

For production you would: create Stripe Products/Prices for the tiers and plans; use `mode=subscription` with a 4-week interval (`interval=week, interval_count=4`) for plans; add a webhook endpoint (`checkout.session.completed`, `invoice.paid`, `customer.subscription.updated`) instead of relying on the redirect; and save a card on file for upsize charges. The pricing research assumed Square for plans, so decide which processor to use.

| Port | `PORT` env var |

Changes to `shared/config.js` need a rebuild (`npm start` rebuilds automatically).

### Renaming / rebranding

Edit `BRAND` in `shared/config.js` (name, lowercase wordmark, tagline, colours). The logo, page title, hero and footer read from it. Also update the colour variables at the top of `web/src/styles.css` (`--navy`, `--aqua`), the `<title>`/favicon in `web/index.html` / `web/public/favicon.svg`, and the "Spun" wording in this README. For example, to switch to Fold Folks, use navy `#1F3A5F` + coral `#F26B5B` from brand-options.md.

## Assumptions taken from the research files

- **Prices are exactly as in `research/pricing.md` §1.2, §1.4 and §2.** All prices are CAD and exclude HST.
  - Small $39, Standard $59, Large $105 (two Standard bags), each extra Standard bag (3rd+) $46.
  - Add-ons: hang-dry $2.50/item, same-day +$25, comforters $25 / $32 / $38 / down $44 / blanket $18, plus free hypoallergenic or own detergent.
  - First Standard bag $39 ($20 off), applied automatically to a customer's first non-plan Standard or Large order.
  - Plans per 4 weeks: Weekly Standard $212, Biweekly Standard $112, Weekly Small $140, Biweekly Small $74.
- **HST 13%.** pricing.md says prices *exclude 13% HST* and recommends voluntary registration, so every total adds a 13% HST line, including plan charges. An accountant should confirm (pricing.md open item 3).
- **Small = one bag only.** Extra bags in the app are Standard bags (on Large). pricing.md doesn't define "2 Small bags".
- **[My assumption] Extra bags on a plan pickup:** $46 for Standard plans and $39 for Small plans. pricing.md doesn't say. The UI doesn't offer extras on plan pickups yet; the pricing logic supports it.
- **Each plan pickup includes 1 bag of the plan tier** (4 bags / 4 weeks = weekly, 2 / 4 weeks = biweekly).
- **Pause.** "Priority windows" is not modelled beyond a fixed weekly slot. Pause takes effect immediately and stops billing. The research says "pause before the next billing date", with no refunds for missed pickups.
- **Pickup windows.** `service-standards.md` only says "2-hour windows". The exact slots come from `research/driver-plan.md` §1.1:
  - Mon–Fri: 7–9 am, 9–11 am, 5–7 pm, 7–9 pm
  - Saturday: 7–9 am, 9–11 am, 11 am–1 pm, 1–3 pm
  - Sunday closed

  Saturday 7–9 am is included because the morning run is listed as "Mon–Sat".
- **Turnaround** follows service-standards §0.5: next day, Saturday → Monday.
  - Delivery defaults to the 5–7 pm window on the next service day (driver-plan: evening = main delivery slot).
  - Same-day needs the 7–9 am pickup and returns by 9 pm. It's Mon–Fri only, because there's no Saturday evening run.
- **[My assumption]** Booking cut-off is 60 minutes before a window starts, and you can book up to 14 days ahead.
- **Service zone.** M8V only (service-standards header; launch-area §1). Fresh Suds (M8Y) sits on the boundary, but its customers' FSA isn't included. Add `M8Y`/`M8W` via config if you widen the zone.
- **Photos.** Photos 1 (pickup) and 4 (delivery) are required for drivers. Photo 2 (partner intake) is optional, and partners can upload it. Retention (90 days) isn't implemented.
- **Bag rules** (must close; soft limit ≈25 lb; split + text before charging) are shown as copy. The upsize charge isn't built.
- **Partner privacy.** The partner sees only the customer ID + preferences (service-standards §2 order sheet).
- **Brand.** Option A, **Spun**, the team favourite: navy `#1B2A4A` + aqua `#3CC6C0`, Nunito/Poppins rounded type, the tagline "Picked up. Spun clean. Back by tomorrow." and the drum/swirl logo, all from brand-options.md. The research flags real risks with the name (slang, ownability, the CIPO search is still pending), which is why renaming is easy.
- `/workspace/spun-site/index.html` did not exist when this app was started (it appeared later), so the styling here is original. The app uses the same brand palette but borrows no code from the site and does not modify it. Aligning the two visually is a possible follow-up.

## Next steps to make it real

1. **Real auth.** Phone or email magic-link login for customers, and staff accounts for drivers/partners/admin (e.g. Auth.js, Clerk or Supabase Auth). Remove the `x-user-id` header.
2. **Hosted DB + file storage.** Postgres, plus private S3-compatible storage for photos with signed URLs and a 90-day deletion job (PIPEDA note §7).
3. **Payments.**
   - Stripe test → live, with Products/Prices, Billing for 4-week plans, webhooks, and a saved card for upsizes and fees.
   - The Customer Portal could handle plan management.
   - HST registration number on receipts.
4. **SMS.** Twilio or similar for pickup/delivery photo texts, overstuffed-bag approvals and missed-pickup scripts.
5. **Ops features.**
   - Overstuffed/wet-bag upsize with photo + customer approval.
   - Claims log (48 h / 7-day windows, $100/$250 caps).
   - Printable order sheets with coloured dots, plus label/tag scanning (barcode on `YYMMDD-NN-B#`).
   - Partner weigh log + weekly invoice.
   - Capacity limits per window.
6. **Routing.** Map view, ETAs and "driver on the way" texts. Real stop ordering (e.g. Google Routes / OSRM).
7. **Before launch, from the research:**
   - Confirm HST treatment with an accountant.
   - Get Measurement Canada confirmation for per-bag pricing.
   - Do a trademark/CIPO + Instagram check on the name.
   - Get partner quotes and the agreement.
   - Have a lawyer review the customer terms.
8. **Tests and hardening.** Unit tests for pricing/slots, input validation, rate limiting, accessibility review and error monitoring.
